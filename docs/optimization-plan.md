# 面向 Agent 成功率的下一轮优化方案

日期：2026-09-13。状态：本轮约定的优化已实现于 remote-mng 0.3.0，验证结果见下表。基线为 remote-mng 0.2.0，参照 sshmng 提交 `8f5a16e80939137a27dfdaeb393cdcfde4e086b3` 的源码与文档。下方各批次保留原验收约定，不能把计划中的期望指标当作实测结果。

本轮采用包含 Python 的目录式发行包，未重写 Go。原方案已明确另行设计的字节级续传、任意多跳/OTP、多目标与团队功能不在本轮交付中。真实企业堡垒机和 CTP 尚无测试环境，不冒充已通过现场验收。

## 目标与范围

用户继续通过 Claude Code 的自然语言任务使用 CLI + Skill，通过本地网页查看与管理状态。服务 Windows 原生、WSL、Linux 的个人试用，支持 SSH/Telnet，工具保持业务通用性。暂不扩展团队功能、多 Agent 安装矩阵或多目标调度。

本轮衡量的是完成任务、准确报告结果、减少重复执行和人工介入。现有 doctor、目标检查、session step 去重、远端 job、任务档案与网页继续复用。不能把已有能力重新计作新增功能。

## 第一批：诊断、Shell 命令与个人安装

### 1. 让 Agent 根据证据处理失败

现状：已有基础检查与错误建议，但若干连接异常仍被归为 timeout/transport_error，登录过程缺少可供修复的阶段记录。

拟交付：

- 在真实连接过程中记录 DNS/TCP、主机密钥、认证、登录步骤、Shell 能力、文件通道各阶段结果；不能把单独探测的成功当作后续连接也成功。
- 错误包含失败阶段、经过脱敏且有大小上限的输出、观察时间、是否已发送业务输入（未发送/已发送/未知）、可用恢复动作和原资源 ID。
- 区分可以重试的只读查询、确认尚未派发的操作、可能已执行的操作；后者优先查询原记录。认证失败不反复尝试同一凭据。
- 配置修复支持校验、修改差异、备份及版本冲突检查；Agent 在原任务授权范围内修正明确问题并复查。凭据、目标身份不从终端输出中自动猜测。
- 网页使用同一份诊断，集中显示待处理事项、最近确认时间、失败位置、证据入口和可交给 Agent 的恢复描述。

验收：缺少凭据、错误密钥、主机密钥变化、端口不可达、登录提示改变、SFTP 缺失分别得到正确阶段与后续动作；脱敏覆盖分片回显；不得通过禁用主机校验或重放未知业务操作来使检查“通过”。

### 2. 同一 Shell 内的命令结束与退出码识别

现状：独立 exec 有退出码但不继承交互会话环境；session step 保留终端状态但输出匹配不等于逐条命令退出码。

拟交付一个专用于已确认 POSIX Shell 的命令接口（具体 CLI 名称在实现时确定）：

- 连续命令保留工作目录和环境变量，同时返回本次输出范围、退出码、请求编号与执行状态。
- 每次命令使用独立完成标记，避免回显、旧提示符和延迟输出被当作当前完成；沿用输入串行控制与请求去重。
- 观察超时保留原请求并继续读取；中断命令作为明确动作处理。无法取得完成证据时保持未知。
- Shell 状态与应用前台模式分开管理。只有确认当前仍是受支持 Shell 时才发送包装命令；进入 CTP/TI 后使用普通交互接口。
- bash、dash、BusyBox ash 分别验证。exit、exec、set -e、终端设置改变、后台并发输出等可能破坏协议，需明确标记能力丢失或未知，不伪造成功。

验收：cd/export 后续有效；非零退出码正确；无换行、ANSI、回显、延迟输出、输出缺口和中途断线不误判；相同请求超时续查的业务计数仍为 1。不能把匹配或退出码 0 当作 CTP 业务通过，也不承诺断线接回原前台。

### 3. 安装、Skill、升级形成一个完整流程

先整合现有安装路径，再验证无需用户管理 Python 的发行包。保留 Python 业务实现；独立发行包通过验证前，源码安装继续可用。

| 路径 | 收益 | 代价与选择 |
| --- | --- | --- |
| 打包现有 Python 与依赖 | 用户无需单独配置 Python；复用已验证代码 | 推荐先验证目录式独立发行包；需逐平台构建、检查资源打包和进程生命周期 |
| 安装器自动管理 uv/Python 环境 | 实施较小，可先改善当前个人安装 | 作为第一阶段和源码安装后备，仍需处理依赖与下载环境 |
| 重写为 Go | 有利于最终单二进制分发 | 会重做 SSH/Telnet、状态与异常恢复验证，当前不选 |

拟交付：

- 一个安装入口完成用户目录安装、Claude Skill 接入、入口绑定和检查；保持机器可读输出，不要求用户记命令。
- Skill 同时识别源码环境和独立发行包，绑定稳定入口。daemon 启动不能继续假定当前可执行文件一定是 Python 解释器。
- 打包网页、helper、Skill 资源，并验证密码学依赖及后台启动。先支持已声明的 Windows/Linux 平台与架构，WSL 按其 Linux 环境验收；明确 Linux 系统库最低要求。
- 私有仓库制品通过已有授权身份获取；校验制品摘要，保持版本固定，不在任务中途静默换版本。
- 升级前检查活动会话、工具/Skill/helper 协议和数据库兼容性。新版本先安装到独立位置，通过检查后切换；失败可回退兼容版本。涉及不可逆数据迁移时不能宣称仅切回程序就能回滚。
- 普通会话会受管理进程重启影响；升级安排在适合断开的时候。已提交的远端 job 保留原目录和 ID，升级后复查。

验收：在不依赖开发仓库和系统 Python 的发行包环境中，完成 Skill 发现、daemon 启动、SSH/Telnet 操作、helper 资源读取、网页打开、升级后查询原任务；验证包含空格、中文及单引号的路径。关闭提交任务的 CLI 后，daemon 和受管 job 的生命周期符合原约定。

PyInstaller 官方说明支持包含解释器的独立分发，但需逐平台构建；单文件模式会解压到临时目录，存在额外启动成本。因此先验证目录式包，单文件形式由实际启动与 daemon 测试决定，不能承诺与 Go 程序相同的体积和性能。

## 第二批：补齐连接覆盖与长期使用能力

### 4. 显式连接路线与登录流程

- 先支持并验证一层标准 SSH 跳板，明确管理跳板和目标的认证、主机密钥、失败阶段及文件通道落点；复用现有 SSH 库，不把 ssh_config 透传视为功能已验收。
- 再增加 HTTP CONNECT/SOCKS5 和有上限的登录决策树：发送、匹配、分支、退出；记录可诊断的失败轨迹。
- 菜单式堡垒机的 Shell 到达目标，不代表 SFTP 也到达目标。传包必须验证独立落点；没有通道时明确不支持。
- 先验证受控菜单变化和正常分支；真实公司堡垒机、OTP、二次认证需现场确认，不承诺任意菜单自动修复。

验收：直连/跳板/菜单目标身份与实际执行一致；跳板故障和目标认证故障可以区分；无传包通道时不会把包误传到跳板。首轮不承诺任意多跳拓扑。

### 5. helper 与网页的长期维护

- 将 helper 协议、路径、最近检查时间、远端空间和日志占用加入能力与状态展示；先补空间预警，再实施日志保留机制。
- 设计每作业日志限额及轮转协议，配套绝对游标和缺口标记。轮转后继续排空输出，不能因停止读取而堵塞业务。
- 清理提供范围预览，只处理明确选定且已终止的作业；默认保留活动和未知作业。删除日志后必须保留证据缺失标记。
- CLI、网页和 Skill 共用相同的恢复动作与证据；网页保留任务观察与有限管理定位。

验收：低空间能定位原因；轮转后不会拼出不存在的成功证据；清理不能误删活动或未知作业；开发者可以从网页明确找到“哪里失败、上次知道什么、下一步是什么”。

## 第三批：按实际传包瓶颈优化

现有工具已有 SFTP 递归和摘要校验；新增重点是受控并发、完整文件清单、总体与当前文件进度、冲突策略和失败文件定位。

优先支持基于摘要核对已完成文件后，继续处理剩余文件。字节级断点续传另行设计源文件与 partial 文件身份校验，不按文件长度直接拼接。保留 SFTP 默认验证；旧 SCP 明确呈现未做端到端摘要验证。多目标中转在个人流程真正需要时再加入。

验收：部分失败可定位到文件，未经核对的 partial 不会发布成正式包；显示传输、校验和部署三个不同阶段；性能指标基于相同产物与网络实测。

## 验证顺序与完成标准

1. 在实现前固定 0.2 基线、Claude Code 版本及模型映射、提示、Skill、目标环境和任务判据。保存失败记录，不能只保留最好的一次。
2. 建立确定性故障用例：缺少 helper、登录失败、回显干扰、超时、提交响应丢失、传包部分失败、本地 daemon 停止、日志缺口和低空间。用独立业务计数/产物/退出文件核对工具报告。
3. 各项实现先通过对应协议与状态回归；新增安装路径必须从实际发行包完成端到端验证，不能只运行源码测试。
4. 对固定场景重复运行 Agent。报告样本数、首次完成率、可恢复故障恢复率、重复业务输入数、结果误判数、人工介入次数、调用数与恢复时间。建议每个场景至少 10 次作为初步观察，不把小样本当作普遍成功率。
5. 测试集中的重复副作用、未知误报成功属于阻断发布的问题。无法自动恢复的场景以准确停留并解释原因为正确结果之一，不强迫所有场景自动“通过”。
6. 有真实设备后补 CTP 验收；前台入口、TI 命令及成功标准由实际项目提供。没有真实设备时只能发布受控环境验证结论。
7. 对 sshmng 做对照仅限双方共有能力，使用同一模型、任务与设备。durable job 等独有能力单列，不将功能缺失混入同类成功率统计。

实施次序：基线与故障用例 → 阶段诊断/网页证据 → 同一 Shell 命令 → 安装升级及独立包验证 → 标准跳板与 helper 存储 → 菜单/代理与传输优化。各批独立交付，不以全部完成为第一次个人试用的前提。
