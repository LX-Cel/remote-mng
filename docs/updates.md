# 更新 remote-mng

日常使用直接对 Claude Code 说：

> 检查 remote-mng 是否有新版，告诉我这次更新的影响。

或：

> 把 remote-mng 更新到最新版。保留现有任务，完成后告诉我版本和验证结果。

随包 Skill 先读取本地安装方式。离线安装会提示需要新版离线安装包，不访问 GitHub；在线安装才查询发布信息并发起下载。开发者通过本地控制台查看组件版本和更新记录，不需要手工拼接资产名和摘要。

## 推荐：运行新版离线安装包

**[0.6.0 预览版](https://github.com/LX-Cel/remote-mng/releases/tag/v0.6.0) 已提供单文件离线安装器。** 下载适合本机系统的新版安装包，按公司要求带入内网后运行：Windows 双击 `...-setup.exe`，Linux/WSL 运行已赋予执行权限的 `...-setup.run`。无需为更新临时连接外网、安装 Python 环境或单独复制 Skill。

安装器从自身读取程序和依赖，检查已有安装与活动，切换版本、同步 Skill 并验证管理器，保留任务、远端 job ID 和个人 `USER.md`。运行同一旧安装包只会核对它自带的版本，**不会获取新版**；必须带入新安装包才能离线升级。只在最后验证成功后报告完成，不能把解包、提交或排队当作安装成功。

离线方式会保存到本地。Agent 的 `update status` 返回 `delivery: offline`；查新或普通更新返回 `blocked`，包含 `offline_update_required` 阻碍和本地安装包指引，不查询外网版本，也不能宣称“已是最新版”。网页显示“通过新版离线安装包更新”，保留本地历史、兼容回退和恢复入口。

离线安装器支持受管独立包的安全更新；旧 uv/Python 环境的离线迁移暂不支持。检测到这类环境后会停止本次安装并说明原因，保留原程序和管理器；不联网下载 wheel、不重装原环境，也不能通过删除 Skill 绑定或卸载原程序来绕过归属检查。运行方式和平台约束见 [安装指南](distribution.md)。

## 可选：在线安装的更新方式

[0.5.0 预发布版](https://github.com/LX-Cel/remote-mng/releases/tag/v0.5.0) 已支持统一入口。安装过之后，在普通系统终端重新运行已下载的同一脚本即可：

Windows PowerShell：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\install.ps1
```

Linux / WSL：

```sh
sh ./install.sh
```

在线脚本会联网选择兼容版本、检查当前活动、安装并同步 Skill、启动并验证管理器。开发者不用自己停止服务、重装 Python 环境或复制 Skill；阻碍仍需按提示处理。脚本来源和首次下载见 [安装指南](distribution.md#可选在线安装)。重新运行在线脚本表示主动选择联网安装方式，后续 Agent 更新恢复使用在线渠道；内网环境继续使用离线安装包即可。

### 更新通道

- **正式通道 `stable`**：只跟随正式发布。首次安装默认优先选择支持新入口的正式版。
- **预览通道 `preview`**：选择最高版本的正式或预发布。当前预览期如果尚无支持新入口的正式版，安装器明确提示后选择兼容预览版；也可主动使用 `-Preview` / `--preview`。

通道会保存到本地。通过预览入口安装后，日常让 Agent 更新仍会跟随预览；无需每次记参数。要切回正式通道，告诉 Claude“之后只跟随正式版”，由它检查并使用 `--channel stable`；通道变化不会自动降级到更旧正式版。高级参数 `--channel preview` 和 `--preview` 是 Agent 的可选显式入口。

公开仓库通过 HTTPS 获取发布信息和精确资产，无需 GitHub 账号或 `gh auth login`。已认证 GitHub CLI 保留为私有仓库的高级后备，认证失败时给出建议，不把 token 放入 URL 或对话。

## Agent 使用流程

先用 `update status` 检查 `delivery`。若为 `offline`，报告当前组件版本与新版安装包指引；用户提供了获准的本地新版安装包路径时，检查活动并运行该包，完成后核对同一安装的状态。不要自行改成在线、查询 GitHub、补下载资源或使用旧的联网计划。下面的查新和计划提交流程仅用于在线安装。

```sh
rmg update status --json
rmg update check --json
rmg update --plan-id PLAN_ID --json
rmg update status --id UPDATE_ID --json
```

`PLAN_ID` 和 `UPDATE_ID` 来自前一次响应。`check` 固定仓库、所选通道的发布版本、平台资产与校验摘要；后续使用同一计划，不因运行中出现另一个新版而改变目标。`update --json` 可直接完成查新和提交。未显式指定通道时使用安装时保存的选择；尚无记录的安装默认正式通道。指定版本可使用 `update check --tag vX.Y.Z --json`；`update check --channel preview --json` 显式选择预览通道。认证信息不写入发布计划或命令参数。

`status` 将实际安装方式和组件状态放在同一个结果中，区分运行中的 CLI、管理器、托管 Skill 和受管安装目录。没有独立安装目录不等于工具未安装。源码环境与独立发行包的可用更新路径以检查结果为准；遇到不支持的安装来源时，工具给出阻碍，不擅自覆盖开发环境。

提交默认立即返回，更新不依赖原 CLI 持续运行。也可以有限等待：

```sh
rmg update --plan-id PLAN_ID --wait --wait-timeout 30 --json
```

等待超时返回退出码 `124`，只停止观察。保留原更新 ID 继续查询，不再提交第二个更新。Ctrl-C 同样不会取消独立更新进程；响应丢失时先看 `update status` 的历史。普通调用退出码 `0` 表示请求完成，仍需核对结果状态。

对于普通 `uv tool install` 安装，更新前会核查环境归属及已安装文件的 `RECORD` 摘要，并将原程序和全部已安装依赖保存为本地离线回退 wheelhouse。由经过校验的独立运行环境执行替换，避免程序重装自己正在使用的解释器。可编辑源码安装、未知 pip 环境、无法验证的文件或自定义环境会明确报告阻碍，保留原环境。

受支持的 uv 更新保留原安装记录中的依赖 constraints；新版本依赖与其冲突时会失败并进入恢复。未知自定义 index、options、extras 或安装了额外工具的环境不会自动覆盖。回退保存并核对原程序、依赖及受管 Skill 字节；原 receipt 和 direct URL 仅保留在私有快照中，不输出私有地址，也不伪造 uv 当前的安装记录。

如果发起命令正在使用需要替换的 uv 环境，`--wait` 会返回 `wait_skipped: true` 并让该 CLI 退出；通过返回的进度页观察，完成后按 ID 查询。不能为了持续等待而占用正在替换的解释器。

## 更新如何处理任务和组件

更新前检查活动交互会话、操作、托管 Skill 完整性和兼容信息。有阻碍时保留现状并报告原因。空闲管理器由更新流程停止并在需要时恢复，开发者不用手工串联停止、安装和启动命令。更新进程独立于管理器，网页暂时断开时可在恢复后继续查询同一记录。

新版需要通过资产和逐文件校验，以及隔离环境中的运行检查。通过后再切换稳定入口、更新托管 Skill，并核对恢复后的管理器。更新来源、目标版本和过程记录保存在本地，供后续查新与恢复使用。

普通 SSH/Telnet 前台不能在重启管理器后自动重接，因此不能为了升级自行关闭正在使用的前台。远端持久 job 不随本地程序切换重新提交；保留原任务和 job ID，更新后继续查询。更新流程不会遍历远端设备并安装 helper；helper 兼容问题在目标检查和作业提交时报告，由 Agent 在目标已有授权、业务确有需要时更新选定目标。

Skill 更新后需要新开 Claude Code 会话，确保后续任务加载新说明。当前会话可以继续查询更新结果，但不能把文件已更新当作会话说明已热加载。

## 状态与恢复

| 状态 | 含义和处理 |
| --- | --- |
| `succeeded` | 本次更新及适用的恢复验证完成，核对最终版本 |
| `blocked` | 存在会话、操作、安装来源或兼容性等阻碍；按记录处理后再发起 |
| `failed` | 更新失败；即使 `recovery.state` 为 `restored`，也只表示旧版已恢复，不能报告升级成功 |
| `interrupted` | 进程或验证过程被中断；依据原记录检查，避免重复安装 |
| `rolled_back` | 用户明确发起的兼容回退已完成，退出码为 `0`；核对实际回退版本 |

更新进程中断，或失败后恢复尚未确认时，使用原失败记录发起恢复：

```sh
rmg update status --id FAILED_UPDATE_ID --json
rmg update recover --id FAILED_UPDATE_ID --wait --wait-timeout 30 --json
rmg update status --id RETURNED_UPDATE_ID --json
```

`FAILED_UPDATE_ID` 来自历史记录；最后一步使用恢复调用返回的 `id`。恢复依据该记录，把安装版本、托管 Skill 和管理器恢复到原状态，只使用已缓存并验证的候选程序、旧版程序或旧 wheel，不查询发布信息、不重新下载包，也不重跑远端任务。所需缓存缺失、内容变化、仍有活动进程或不能验证兼容性时会停止并说明原因。

恢复成功只表示本地安装恢复，不能报告原升级已经完成。检查返回的版本与恢复验证结果；不能手动删除 `update-switch.json`、改版本指针或重新提交远端作业来清除异常。此入口同样支持有限等待，超时后继续查询返回的恢复记录。

显式回退也通过同一更新流程执行：

```sh
rmg update rollback --json
rmg update rollback --to-version X.Y.Z --json
```

回退只使用保留且通过验证的兼容版本。程序与 Skill 回退不等于数据库恢复；未知数据库结构、协议变化或缺少兼容路径时拒绝切换。当前更新不做隐式数据迁移，也不删除任务、日志或远端作业。

离线方式的自动联网拦截需要 0.6 及之后版本。回退到更早版本后，继续使用离线安装包维护，不要假定旧版 `update` 已具备新的离线策略。

如果恢复或回退到尚无 `update` 命令的旧版（例如 0.3.0），旧 CLI 不会因此获得更新功能。保留独立更新器或安装入口，后续维护从该入口进行；不要删除这次恢复仍需使用的缓存。

部分 Windows Agent 宿主禁止新建独立进程。更新流程在最终执行进程中、停止原管理器和切换版本之前，使用与正式启动相同的独立进程参数执行一次只读运行时检查。若宿主拒绝，会报告阻碍并保留原版本及正在运行的管理器；不会等到替换程序后才首次发现这一限制，也不会把普通子进程能运行当作独立启动验证通过。

这个检查确认的是当时的独立进程创建能力，不能保证之后宿主权限不会变化，也不代替新版功能健康检查。初始更新进程本身无法启动时仍会返回 `update_worker_start_failed`；后续管理器启动失败与更新进程启动失败会分别报告，结合更新阶段、实际版本和恢复状态判断结果。需要在允许的普通终端环境发起时，按记录建议处理；不能通过计划任务、其他宿主进程或反复启动绕过限制。预启动过管理器也不能证明后来接手的更新进程具有相同权限。

uv 更新与恢复使用已验证的独立更新器做该启动能力检查，不要求可能损坏的 uv 环境先运行成功；它不表示待恢复的 Python 环境已经健康，程序和 Skill 的健康状态在实际安装或恢复后另行验证。

## 保留个人 Skill 约定

个人补充说明默认放在 `~/.claude/remote-mng/USER.md`；设置了 `CLAUDE_CONFIG_DIR` 或 `--claude-dir` 时位于所选配置目录下的 `remote-mng/USER.md`。`rmg skill status --json` 返回实际路径及可读状态，安装后的 Skill 指向该路径。

此文件由用户维护，可以写入部署规范、业务成功判据和操作偏好。工具不会自动创建、读取、覆盖或删除其内容，Agent 按 Skill 说明在文件存在时读取。它不参与托管文件摘要，因此修改不会阻碍升级。不要在文件中存密码、私钥等凭据。

已经直接修改过 `skills/remote-mng` 的用户仍会收到完整性冲突。原文件不会自动迁移；先保留副本，将需长期保留的个人约定整理进 `USER.md`，恢复或移走改动过的托管目录后再安装。不能删除安装清单或用强制覆盖来跳过保护。

## 从没有 update 命令的版本开始

0.5 新入口可在不要求旧 CLI 已有 bootstrap 命令的前提下引导迁移；实际安装前先检查来源、管理器活动和兼容性。正在运行的 0.3 管理器缺少维护预留协议，入口会明确阻碍，不会为了更新自动强停。让 Agent 核对会话、操作与原 job ID，在你确认普通前台可以断开后处理，再运行同一脚本。

旧版普通 uv 安装（至少 0.4、归属与文件可核验）会先保存原程序和依赖的离线快照，再由独立候选安装器执行安全更新；可编辑和未知环境不自动覆盖。Windows、WSL 的官方 0.4 到 0.5 前台升级及重复安装已通过，具体范围见 [0.5 验收记录](v05-validation.md)。其他显式源码维护见 [高级源码步骤](claude-skill.md#源码手工维护)。

维护者应对每次正式制品变更递增版本，发布与 ZIP 匹配的摘要，并验证上一正式版升级到候选版的路径。同名同版本但内容不同的包会被拒绝；不能把替换旧资产当作版本更新。发布检查结果与支持范围仍应随版本记录，测试夹具通过不等于真实设备和所有旧版本均已验收。

发布 CI 默认要求真实 uv 环境完成升级和离线回退。在限制独立进程创建的宿主中，可以显式为 `scripts/smoke_source_update.py` 添加 `--expect-process-block`，只验收 `independent_process_unavailable` 在停止管理器和替换程序之前发生，并检查原管理器 PID、安装文件、Skill、任务及个人说明保留。此诊断结果标记为 `passed_blocked_safely`，表示保护生效，不能称为升级成功，也不替代默认 CI 的完整更新验收。
