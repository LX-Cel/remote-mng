# 0.3 实际 Claude Code CLI 验证

日期：2026-09-13。本轮使用真实 Claude Code CLI、已安装 Skill 和 Windows 独立发行包，控制 WSL 中的真实 SSH/Telnet PTY。没有调用 MCP，也没有把源码单元测试当作 Agent 完成任务的结果。

## 环境与判据

- Claude Code：`2.1.218`。当前账号提供方映射的主模型为 `glm-5.3[1m]`；部分运行记录含 `glm-5.2[1m]` 辅助调用。不能据此声称原生 Claude 模型具有相同结果。
- 消费项目位于开发仓库之外的 Windows 临时目录，路径含中文、空格、单引号。每次使用独立 `CLAUDE_CONFIG_DIR`、`RMG_HOME`、目标配置和远端业务目录。没有修改用户的全局 Skill 或 Claude 配置。
- 从 ZIP 经真实安装器安装，再通过安装生成的 Skill 包装脚本调用稳定入口。消费项目故意包含会抛错的 `remote_mng.py`，检查发行包不会导入项目中的同名模块。
- 每次最多 420 秒，两次并行。允许工具为 `Skill(remote-mng)`、`Read`、Skill 包装 CLI 的 `Bash`；`dontAsk` 权限模式，严格空 MCP 配置。不通过其他远程工具替代失败操作。
- SSH/Telnet 服务仅监听本机 `22334/23334`，远端是 WSL 中受控的 `/bin/sh`。没有真实 CTP 设备、公司堡垒机或生产服务器。

固定业务场景：创建任务 → 打开会话并确认 Shell → `cd` 和 `export` → 执行 `./once.sh`，首次观察窗口为 0.05 秒 → 使用同一会话、命令、request ID 和任务 step ID 继续观察 → 在同一 Shell 检查目录、环境和计数 → 关闭会话、seal 任务并报告。

`once.sh` 向自己的计数文件追加一个 `X`，等待 2 秒，再输出该次唯一的 `ONCE_DONE`。业务通过必须同时具有退出码 0、正确完成输出、正确目录/环境和计数 1。运行器之后直接在 Linux 主机读取计数文件，独立于 Agent 和 remote-mng 的报告核对副作用。完整工作流还要求原步骤只有一次执行、任务已 seal、连接已关闭、Agent 正常结束并如实报告，包括已恢复的错误。

实际收尾中，Agent 先发送 `exit`，再读 EOF，再调用 `session close`；旧版对已断开的会话返回 `session_disconnected`。这种流程额外消耗调用，与 18 turn 预算共同阻碍收尾。新版已经允许对已知历史会话幂等关闭，并明确普通 Shell 直接 close；应用前台仍遵循真实退出 profile。这组原始失败记录保持不变。

### 调用成本观察

代表性的 21 次调用由 Skill 加载、首次 doctor、读取目标文件、读取 4 份参考、目标查询/登记/检查、创建任务、打开/观察/启用 Shell、4 次业务执行或续查、3 次收尾组成。预启动之后没有再次启动管理进程的循环。

可减少的部分主要是普通 Shell 被同时路由到应用交互参考、没有部署/传包需求时额外进行完整目标检查、以及 `exit → 读 EOF → close`。直接 close 可以省去两次收尾调用。Shell 模式确认、原 ID 续查、业务证据和目标身份检查不能为了降低调用数而省略。

## 修复后发行包的完整工作流跟进

试验包 SHA256：`ea39ea93ace1291ca1e8b5dc7b3090c61b6e773ea8bcb0e888048f3d88aa717b`。使用独立的新目录与请求编号，SSH/Telnet 各一次，预算为 **32 turn**。包包含幂等 close 和更新的 Skill：普通 Shell 直接 close、按需读取参考、无部署或传包需求时不额外探测无关能力。提示也明确直接 close。

| 试验 | 协议 | 用时/秒 | 工具调用 / turn | 业务与收尾 | 报告准确性 |
| --- | --- | ---: | --- | --- | --- |

两次均发现已安装 Skill、未调用 MCP、正常结束；超时后同 ID 续查、同一任务步骤只执行一次、目录/环境继承及独立计数全部通过。重复业务输入 **0**、权限拒绝 **0**、业务结果误报成功 **0**。

**执行与收尾为 2/2；把错误披露也纳入完整交付，则为 1/2。** SSH 试验先错误地为 `session read` 添加 `--token`，得到 `invalid_arguments`；随后又添加 `--task`，得到 `task_method_denied`。修正后取得正确证据，但最终答复声称除预期超时外没有其他错误，遗漏了这两次已恢复错误。Telnet 试验没有这两项问题。业务正确与总结准确性应分开核对。

用时中位数为 **67.095 秒**，工具调用中位数为 **21 次**。与固定 10 次相比，普通 Shell 的退出循环和无关检查减少，但 SSH 参数试错、额外帮助查询仍消耗调用；两次实际 turn 数仍超过 18。样本量、预算、Skill、提示与收尾实现同时变化，不能归因于单个修复，也不能据此声称完整成功率已经稳定。

本轮之后发布包又补充了 cleanup 计划与目标配置的绑定、`session read` 的正确参数示例，以及要求总结已恢复错误的 Skill 说明。目标绑定有确定性回归，新增 Skill 文案没有再次进行真实 Agent 试验；不能声称已经消除上述漏报。保留本节实际运行的包摘要，不用后续包替换试验身份。

## 证据与适用边界

本地原始证据保存在忽略提交的 `.test-state/v03-agent-acceptance`、`.test-state/v03-agent-acceptance-fixed`、`.test-state/v03-agent-acceptance-followup`。包括安装记录与 ZIP 摘要、每次提示摘要、已安装 Skill 文件摘要、模型/版本、经过脱敏的流式事件、工具调用、任务步骤、CLI 结果、独立计数及汇总。凭据仅传入进程环境，未写入公开文档；会话控制令牌在事件证据中脱敏。

小样本只证明这个模型映射、宿主权限、固定流程和实验设备上的结果。没有无条件的“Agent 成功率提升百分比”，没有与 sshmng 的同任务对照，也没有真实 CTP 兼容性结论。低 turn 预算下完整交付不足是本次发现的实际问题。

Shell 协议、helper 轮转/清理、同 ID 去重和断线状态另有确定性测试，详见 [Shell 协议说明](shell-v03.md) 及测试源码。它们与本页的真实 Agent 工作流结果分别报告。
